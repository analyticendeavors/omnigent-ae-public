# Blocking internal identifiers (2026-10-28)

Nothing internal may reach the public fork or the public release: no IP, host name, e-mail address, home path, cloud id, private repository name, secret, client or person's name. The admin portal and the box-health work read box internals, and a second person shares the box, so the old check (a fixed list scanned by hand when a release is prepared) was too late and too narrow. Two facts drove this change:

- Every patch PR pushes its commits to the public fork `analyticendeavors/omnigent` as a topic branch **before** any check runs. A release scan days later cannot pull that back.
- This repository's CI had no leak check at all, so a leak landed on private `main`, surfaced at release, and cost a fix and a new tag.

`scripts/leak-scan.py` (stdlib only, Python 3.11 or later) closes both. It runs in CI on every PR and every push to `main`, in the `pre-push` hook on the box (the superproject and `upstream/`), in `scripts/fork-push.sh`, hourly against the fork itself, and by hand with `just leak-scan`.

It **never prints a matched value**. A hit reads `path@commit:line: class rule-id`, at most 50 lines, then a count per class; the full list (still without values) goes to the job summary in CI or to `--report FILE`. Every name it shows (file, branch, tag) has the matched value replaced by `***`, in the hits, the workflow annotations, the summary, the report and the error messages alike. That is what lets the check run in a public log.

## Where it runs

| Where | Command | What it reads |
|---|---|---|
| A pull request (`leak-pr.yml`, job `leaks`) | `diff --base B --head H --title-env PR_TITLE --body-env PR_BODY` | every commit in `B..H` on its own: its author and committer, its message, the paths and added lines it brings; then the PR title and body. Runs on opened, synchronize, reopened, edited, labeled, unlabeled and ready for review, with the base commit's scanner and the base commit's allowlist |
| Push to `main` (`ci.yml`, job `leaks`) | `diff --allowlist-from head --no-identity --base <before> --head <sha>`, then `tree --ref HEAD` | the pushed commits' messages and lines, then every tracked file and path; a hit turns `main` red, which stops `release.yml` from tagging. Commit authors are not checked here (2026-10-29): a merge commit's author is the merger's GitHub address, and main's history never goes public |
| `pre-push` hook | `push <remote> <url>` | every commit going to **that** remote (a commit already on the private origin is new to the public fork), the ref names, an annotated tag's message |
| `just fork-push BRANCH` | the same check, run by the script | the same, without relying on the hook being installed |
| `fork-backstop.yml`, hourly | `fork --base <upstream sha> --state ...` | the public fork's branches, commits new since the last clean run; `AE_LEAK_SCAN_SECONDS=900`, because the first run reads every branch |
| By hand | `just leak-scan <subcommand> ...` | `diff`, `tree`, `text FILE...\|-` (release notes, a PR body), `media FILE...` |

**The allowlist is the base commit's** (second review, 2026-10-28). An entry a PR adds or changes clears nothing in that PR, and is a failing finding of its own (class `allowlist`, named by class and path glob, never the pattern), because a PR that allowlisted its own leak would pass otherwise. A reviewer approves it by applying the label `leak-allowlist-approved`; the check then re-runs (it also triggers on `labeled` and `unlabeled`) with the PR's allowlist in force and lists each entry as a notice. The approval counts only if the actor of the label's latest `labeled` event, read from the PR's issue events with the job's token, has a numeric GitHub user id in the repository variable `AE_LEAK_ALLOWLIST_APPROVERS` (comma separated, passed through `env:`). Unset or empty means nobody can approve, so new entries always fail. Retargeting the PR (an `edited` event with `changes.base` set) voids it the same way, and a label that cannot be removed fails the job. A later push that changes `scripts/leak-allowlist.txt` voids the approval: the job compares the file at `github.event.before` with the new head (both values come from GitHub, so a commit date cannot forge them), removes the label, and the approver applies it again. A push's run has a concurrency group of its own so another event cannot cancel the removal. The PR that introduces the scanner has no base scanner or allowlist, so it uses its own.

**Images in a PR are read with OCR** (2026-10-29). After the diff scan, `leak-pr.yml` lists the image files the PR adds or changes (the `media` suffixes; deleted files are skipped). If there are none, nothing more runs. Otherwise it installs `tesseract-ocr` on the runner and runs the base commit's scanner as `media --ocr require` on those files from the head checkout, with the base allowlist and the same denylist arguments. A hit fails the job like the diff scan, and no matched text is printed. An animated WebP is read frame by frame (`anim_dump` from the `webp` package, each distinct frame once), because tesseract decodes only still WebP. OCR runs in CI only, not in the pre-push hook or on the box.

A value added in one commit and removed in the next is caught: the net diff is never what is scanned. A merge commit contributes only the lines neither parent had, so merging `main` into a topic branch does not rescan `main`.

Exit 0 is clean, 1 means hits, 2 means the scan itself failed: an unreadable input, a bad bundle or allowlist, a push range that cannot be computed (an unknown remote tip, a line git passed that does not parse), a `git diff --raw` output it does not understand, a denylist whose hash does not match, a scan past its 120 s limit. A failure never reads as clean.

`upstream/` is a gitlink and is never scanned; its content reaches this repository only as `patches/`.

## The classes

| Class | What it finds | Cleared by |
|---|---|---|
| `denylist` | the private fixed strings (case-insensitive); the hit names the entry number only. Also a commit author or committer name | nothing: fix the text or change the private list |
| `secret` | shapes for GitHub, GitLab, Anthropic, OpenAI, AWS, Azure keys and SAS signatures, Entra client secrets, Slack, Tailscale, Databricks, Hugging Face, npm, Google, Stripe, HubSpot, Mailchimp, Cloudflare tunnels, JWTs, `Bearer` tokens, and a `secret`, `token`, `password`, `api_key` or `credential` keyword (in code, YAML, env files or JSON) assigned a 20+ character value | nothing |
| `private-key` | PEM and OpenSSH private key headers | nothing |
| `tailnet-host`, `tailnet-ip` | `*.ts.net` names; single addresses in 100.64.0.0/10 and fd7a:115c:a1e0::/48, in any context except a `/<prefix>` suffix | allowlist or marker |
| `lan-ip` | single RFC1918 addresses, including `http://<ip>/api` and `user@<ip>` (a `/<prefix>` suffix and version strings such as `v1.2.3.4` are skipped) | allowlist or marker |
| `internal-host` | `*.local`, `*.lan` and `*.internal` host names (not `host.docker.internal`, file names such as `x.local.yml`, or code such as `self.local`) | allowlist or marker |
| `email` | any address (systemd `name@instance.service` units are not addresses) | allowlist or marker |
| `commit-identity` | a commit author or committer address that is not a noreply or bot address | allowlist (`commit-identity <address>`) |
| `home-path` | `/home/<user>`, `/Users/<user>`, `C:\Users\<user>`, `/c/Users/<user>`, `/mnt/c/Users/<user>`, and the Claude project-dir forms `-home-<user>-` and `C--Users-<user>` | allowlist or marker |
| `azure-endpoint` | Key Vault, Entra, Storage, App Service, Databricks, Service Bus, SQL and Container Registry host names, and tenant or workspace ids in sign-in and Fabric URLs | allowlist or marker |
| `cloud-id` | every non-placeholder GUID outside lockfiles, `node_modules`, `dist`, vendored and generated files, and a 32-hex id on a line that names a tenant, client, app, subscription or object | allowlist or marker |
| `private-repo-link` | `analyticendeavors/<name>` anywhere (a URL, a clone address, a workflow `uses:` or `repository:`, an API path) unless listed in the allowlist | allowlist or marker |
| `path-name` | the denylist, e-mail, host and IP classes applied to a file path (the path is shown with the match replaced by `***`) | allowlist |
| `binary` | a new or changed binary file that is not an image, a PDF or a font | allowlist, by exact path only |
| `media-metadata` | EXIF, XMP, IPTC, comments, colour profiles, unknown chunks and bytes after the end of the image in PNG, JPEG, WebP, GIF, TIFF, HEIC and AVIF files; PDF Info and XMP; an image that does not parse | allowlist (by the value's hash) |
| `media-text` | text OCR reads from an image, when `tesseract` is installed | the class it matched, as above |

Public addresses outside the documentation ranges are a **warning**, never a failure. Documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32), loopback, `example.com`, `example.org`, `example.net`, the `.example`, `.invalid`, `.test` and `.localhost` names, noreply addresses, `git@<host>` clone URLs, `host.docker.internal`, systemd unit names and obvious placeholders are built in and never hit. A host name counts as a placeholder only when the label that identifies it is one (`<anything>.tailnet.ts.net`, a made-up vault name under the Key Vault domain); a placeholder elsewhere in the name does not excuse the real label.

### Patch files

`patches/*.patch` hold upstream's own code around ours. Only the lines a patch adds (the `+` lines) and its commit header get every class; context and removed lines are upstream's, so they get the denylist only. A commit body that contains a bare `---` line stays part of the header: the header ends where a diffstat or a diff begins. Author lines in a patch header (`From:`, `Signed-off-by:` and similar) are exempt from the e-mail class.

## Clearing a false positive

Fix the text first: use a documentation address, a placeholder name, or a generated value. If the value is genuinely safe, there are two reviewed ways to say so. Every one is visible in the PR.

1. **Allowlist line** in `scripts/leak-allowlist.txt`: `<class> <pattern> [path-glob] # reason`. The pattern is, in order of preference:
   - `sha256:<hex>`, the sha256 of the lower-cased matched value. Run the scan with `--hash-hits` and each soft hit prints the hex to use; the value is never printed. Use this for any real value: the file is public.
   - a literal (matched case-insensitively, `*` and `?` allowed) for a public or made-up value, in the classes other than the ones below. It needs at least 4 characters besides wildcards (a regex, at least 4 fixed characters outside classes and operators).
   - a `/regex/`, in those same classes. The scanner refuses one that matches almost anything (`/./`, `/.*/`), because that would clear a whole class for a whole file.

   `email`, `commit-identity`, `lan-ip`, `tailnet-host`, `tailnet-ip`, `cloud-id`, `home-path` and `azure-endpoint` take **only** `sha256:` entries: a wildcard there (`lan-ip *`) would clear every address or id of the class (second review, 2026-10-28).

   The reason is required and must not name a private value. The path glob limits the entry to matching files. A `binary` entry is an exact path with no glob. A hash of a short or guessable value (an address, a user name) can be reversed by trying candidates: it hides the value from a search, not from a determined reader.
2. **Inline marker** on the same line or the line above: `leak-scan: allow=<class> reason="<why>"` (several classes separated by commas). The reason is required. A marker clears only what a PR adds: one on an unchanged line does not cover a new line below it. CI lists every new marker in the job summary.

Neither can clear `denylist`, `secret` or `private-key`. A marker that names one of them, or has no reason, is itself a hit. The scanner also refuses to run (exit 2) if the allowlist text contains a denylist entry or any line matches one, so the public file can never carry a private value and a tag cannot exempt itself. The allowlist file is itself scanned (an address pasted into a reason hits); only each entry's own pattern field is exempt.

Entries marked `DECISION` in `scripts/leak-allowlist.txt` name a real value that was found on `main` when this check landed. As of 2026-10-29 the install path and the cloud ids are gone from the repository's own files (the units carry an `__AE_HOME__` token the installer renders; the ids are box settings), so the entries that covered them were deleted. Two remain, for fork patch files whose `+` lines keep a fixture path and a fixture host. They exist so CI is green; delete the line when the value is gone.

## The private denylist

The denylist itself is private and lives outside this repository (the private release tooling). It reaches the scanner as a *bundle*, one entry per line, `#` for comments. An entry may start with `@outside-patches ` (not applied to `patches/`, for values the fork already published) or `@new-lines ` (applied to added lines, commit text and prose only, not to the existing tree; for a backlog that cannot be cleaned in one PR).

- **CI** passes the repository secret `AE_LEAK_DENYLIST_B64` (base64, one line, so GitHub's masking holds) and the repository variable `AE_LEAK_DENYLIST_SHA256` to the scanner (`--denylist-b64-env`, `--denylist-sha256-env`). The scanner decodes it in memory, checks the hash, and fails with exit 2 if the secret is set and the variable is not, or if they disagree (the two were updated separately). A **missing secret fails the job** (`--denylist-missing fail`, in `ci.yml`, `leak-pr.yml` and `fork-backstop.yml`; 2026-10-29, once the secret and variable were set; it warned and ran the generic classes only before). Dependabot-triggered runs read the **Dependabot copy** of the secret (a separate store), so it is set there too, or those PRs fail. A pull request from a fork cannot read the secret, so it fails closed (exit 2); that is intended, because this repository is private and its PRs come from branches. The denylist step is keyed on the repository id, not its name, and is absent in the public repository.
- **Which scanner runs.** On a PR the job checks out the base commit into `base-scanner/` and runs *its* `scripts/leak-scan.py`, so a PR cannot edit the scanner to print the denylist it is handed. The allowlist is the *base* commit's (`leak-pr.yml` "Trust boundary"), so a PR cannot clear its own hits: an added or edited entry fails the scan unless an approver's label is on the PR, and then the head's allowlist is in force. Every entry a PR adds is listed in the job summary by class and path (never its pattern). A base with no scanner (the PR that introduces it) runs the head's.
- **Builders** point `AE_LEAK_DENYLIST_FILE` at a bundle file, or put one at `~/.config/omnigent-ae/leak-denylist.txt`, and pin its hash with `AE_LEAK_DENYLIST_SHA256` or a `<bundle>.sha256` file (write it with `sha256sum <bundle> | cut -d' ' -f1 > <bundle>.sha256`; the private release tooling writes it next to a fresh bundle). **A bundle with no pin refuses the push too**, because a stale or edited bundle would pass unnoticed. With no bundle the hook **refuses** the push; a clone that has no access to the private denylist sets `AE_LEAK_ALLOW_NO_DENYLIST=1` to run the generic classes only, with a warning.

## Builders: the pre-push hook and `fork-push`

Run `just hooks-install` once in the clone you push from. It sets `core.hooksPath` to `scripts/hooks` for the repository and for `upstream/`, so a push from the submodule to the public fork is scanned too. `core.hooksPath` is shared by every worktree of a clone; run it in the main clone, not in a worktree you will delete.

What a push scans (2026-10-29): a new branch scans every commit not on any of the destination's remote-tracking branches; an update scans every commit not reachable from the branch's current tip on the remote or from the destination's default branch (`<remote>/HEAD`, else `<remote>/main`, as this clone last fetched them). So a branch that merged `main` does not rescan `main`'s squash commits, whose author check `main`'s own scan skips, while a commit held under any other tracking ref is scanned again, since that branch may have been deleted on the remote. A commit held only by another remote is always new to the destination: the private origin's commits are new to the public fork. After pointing a remote at a different repository, run `git fetch --prune <remote>` and `git remote set-head <remote> -a` before pushing, so its tracking refs describe the new one.

A hook is not enforcement: it does not run for `git push --no-verify`, in a clone that never ran `hooks-install`, or for a push through the GitHub API. So `just fork-push BRANCH` (or `scripts/fork-push.sh BRANCH` inside `upstream/`) runs the same check itself before it pushes and refuses on a hit. It passes only `-f`, `--force-with-lease` and `--force-with-lease=<ref>:<sha>` on to `git push`; `--tags`, `--follow-tags`, `--all` and the rest are refused by name because they would push refs the scan never saw. A deliberate `--no-verify` push from a hand-made clone is **still caught only by the hourly backstop**, after the branch is public (below).

## The fork backstop

`fork-backstop.yml` runs hourly on the private repository. It fetches every branch of the public fork, scans each commit that is new since the last clean run (all of them on a first run, with no saved state) with the denylist, and on a hit fails the job and prints `public fork branch to delete: <branch>` with the branch's tip commit. Delete the branch (`git -C upstream push origin --delete <branch>`) and, if a secret was in it, rotate the secret: the commit was public for up to an hour. Each unique commit is scanned once per run and its hits are reused for every branch that carries it (2026-10-29): the fork's branches share most of the patch series, and scanning it once per branch ran out of the job's 15 minutes. The fork also holds copies of upstream's own branches, whose history is public upstream code and not ours, so the workflow fetches upstream's heads and tags (from `upstream.lock`) and passes `--exclude-refs refs/remotes/upstream/ --exclude-refs refs/remotes/upstream-tags/`; everything reachable from them is left out of every branch's range (2026-10-29: that took a cold run over the fork's 1,950 branches from 5,959 commits to 592, and from over 15 minutes to about 4). Two fork-mode rules follow from the same fact. The e-mail half of the commit-identity check applies only to AE's own commits, the ones whose subject starts with `[ae-patch]`, because a fork branch that upstream deleted can still hold upstream commits by authors whose addresses are not ours to police (on 2026-10-29, 201 of the 600 commits outside upstream's refs lacked the prefix and 84 of those had non-noreply addresses, mostly upstream contributors'). The denylist half runs on every commit's author and committer, prefixed or not, and every other class still applies to every commit; one notice per run counts the commits whose e-mail was not checked. And `@outside-patches` denylist entries are skipped, the same meaning they have for `patches/`: they name values the fork already published, so a rebase that mints new shas of those old commits would otherwise list most fork branches for deletion every hour. `--exclude-refs` is validated: each prefix must end in `/`, must not equal, contain or sit inside the fork's own refs, and must match at least one ref, or the scan exits 2. The workflow also refuses an empty `UPSTREAM_REPO`, one equal to `AE_FORK` or owned by analyticendeavors, and a fetch that brings no upstream branches. An AE commit that also lands on an upstream ref is excluded from the backstop; it is already public upstream. The saved state is a speed-up and no longer the thing that keeps the job green: it holds branch and tip pairs, is written only after a run with no new hit, and losing it costs one full rescan (about 190 s cold, against 900 s before the baseline below). A new hit keeps failing every hour until the branch is gone. `patch-rebase.yml` pushes rebased fork branches with its own token and runs no code from the checkout; it adds no new content, and the backstop covers it.

### The fork baseline (2026-10-29)

On 2026-10-29 a cold run over the fork (1,952 branches, 599 commits outside upstream's refs) found 200 soft hits in 96 commits (79 of them upstream-authored, 17 `[ae-patch]`) and failed every hour, and every patch PR rebases its series into new shas, so no key built on shas stays valid. The owner decided to accept what the fork already carried once and to fail only on new leaks.

- **The file.** `scripts/leak-fork-baseline.txt`, one line per value: `<class> sha256:<hex> # fork baseline, seen in <where>`. The key is the class and the hash of the lower-cased value (the same hash as an allowlist `sha256:` entry), never a commit, a path or a date, so a rebase, a renamed file or a lost cache changes nothing. The comment says where the value sat (a file path, `commit message`, `commit identity` or `branch name`) for reviewers only and is not part of the key.
- **Fork mode only.** `fork --baseline FILE` counts a soft hit whose class and hash are listed, prints `notice: fork baseline accepted <n> hit(s) in <m> commit(s): <class>=<count>, ...` and does not fail on it. Every other hit is new: the branch is listed for deletion, the summary line says `with new hits`, and stderr says the baseline is not a way to clear it. The PR check, the push-to-main check, the pre-push hook and `fork-push` do not read the file and keep using the allowlist, so AE's own work is still stopped before it reaches the fork. On a run with no saved state a second notice counts the baseline lines that matched nothing, for pruning.
- **A baseline never accepts a hard class.** `denylist`, `secret` and `private-key` lines, a `marker` or `allowlist` line, an unknown class, a malformed hash, a missing reason or a repeated line is exit 2. So is a file that contains a denylist entry as text, or a line whose hash is the hash of a denylist entry. A secret in the fork is fixed by deleting the branch and rotating the secret, never by a baseline line. A soft value that only contains an `@outside-patches` entry cannot be told from its hash and is accepted by policy, since those values are already published.
- **Regenerating it.** `fork --base <sha> --write-baseline FILE`, on a machine that has the private bundle, after fetching the fork and upstream the way `fork-backstop.yml` does. It needs a loaded denylist and refuses `--state` and `--baseline`, so it is always a full, fresh scan. It ignores the allowlist and inline markers, so a later edit to either never re-opens an old commit. It writes the header and the sorted, deduplicated lines, byte for byte the same on a re-run, and prints counts by class, never a value or a hash. While any hit cannot be baselined (a hard class, a marker problem, a hit with no hash) it writes nothing, exits 1 and lists the branches. Regenerate in the same PR whenever a new scanner rule would hit old fork commits, or the backstop turns red.
- **Approval.** Any change to the file, added or removed lines, needs the `leak-allowlist-approved` label from an approver, like the allowlist: `leak-pr.yml` fails a PR that changes it (a three-dot diff, so the PR that introduces the file is covered) and a push that changes it removes the label. The workflow cache key holds `hashFiles('scripts/leak-fork-baseline.txt')`, so an edit forces one full rescan.
- **Keep it out of the public release.** The file gathers into one list hashes of values that are public on the fork one by one, and a hash of a short or guessable value (an address, a name) can be reversed by trying candidates. The release tooling (`sync-public.sh` in the private tooling repository) leaves `scripts/leak-fork-baseline.txt` out of the public release.

## Images, PDFs and other binaries

`media` reads PNG chunks, JPEG segments, WebP chunks, GIF blocks, TIFF tags, HEIC and AVIF boxes and PDF Info with no imaging library. Metadata (EXIF, XMP, IPTC, comments, PNG text, unknown chunks, colour profiles, bytes after the end of the image) is flagged except ffmpeg's `Lavc` encoder comment and the one sRGB profile the committed JPEGs carry (allowlisted by its hash). `just leak-strip <files>` rewrites an image in place without that metadata and without the colour profile; the pixels stay byte-identical. Do not mass-strip images that are already committed: changed bytes send every image back through the release's image gate.

A new or changed binary file that is not an image, a PDF or a font is a `binary unreviewed` hit until someone allowlists its exact path. Text in UTF-16 with a byte-order mark is decoded and scanned. Base64 or otherwise encoded text is not decoded.

OCR runs when `tesseract` is on `PATH` (`--ocr auto`, quiet when it is absent). It helps a human look at a screenshot and never replaces the look: OCR misses small and low-contrast text. Pixels and video stay on the human gate at release.

## Known gaps

- A static scan cannot enforce runtime isolation between users (what the Admin Center shows to whom). That belongs in the feature's own tests and the admin gate.
- It sees text it can read. A value split across lines, base64-encoded, or only in pixels needs a person. Video and most other binaries stay on the human gate.
- `--no-verify` and API pushes skip the hook and `fork-push`; only the hourly backstop sees them, after the branch is public.
- A repository without the denylist secret fails CI (2026-10-29). Keep the secret in both the Actions and the Dependabot stores, and rotate it in both.
- A person's first name or a bare private repository name is not a generic class; those belong in the denylist's `@new-lines` scope until the backlog is renamed.
- Links to the second owner's personal repositories are caught only by the private denylist (removed from the generic `private-repo-link` class on 2026-10-29), so a clone running with `AE_LEAK_ALLOW_NO_DENYLIST=1`, or CI without the secret, does not see them.
- A red `leaks` check advises until a ruleset on `main` requires it (the check name is `leaks`).
- A PR can edit the workflow that runs the scanner (or the scanner, or the allowlist), and the `pull_request` event runs the PR's own workflow file. The fix is a repository ruleset with required review on `.github/workflows/`, `scripts/leak-scan.py` and `scripts/leak-allowlist.txt`; that is a repository setting for the owner. `.github/CODEOWNERS` (2026-10-29) assigns those paths, and itself, to the organization team `leak-approvers`, a separate person from the account that opens every PR, and has no catch-all line (the box account could never approve its own PR). A ruleset requiring code-owner review and the `leaks` check follows once that file merges; until then the file asks for the review and does not enforce it.
- After an approval, a failed synchronize run and a passing labeled run can both report a `leaks` check on the same sha. Confirm on the first labeled PR which one the ruleset reads.
- The approval label is removed by the push's own run. A run for another event in the seconds before it finishes can still see the label.
- `.heic`, `.heif` and `.avif` images get no OCR (the runner's tesseract cannot read them, and `--ocr require` would fail a clean file). Their metadata is still checked: every scan that reads a blob, the diff scan included, runs the `media-metadata` checks on all `media` suffixes. Text in their pixels needs a person.
- OCR runs in CI on a PR's changed images only. The pre-push hook and `fork-push` do not run it (no `tesseract` on the box), so an image pushed to the public fork is read by OCR only if its PR scan ran, and the hourly backstop does not OCR.
- The backstop writes no state while no denylist is loaded, so every commit is scanned again once the secret is set.
- Two fork patch files still carry a fixture home path and a fixture host in their `+` lines, under `DECISION` allowlist lines; they go when the series is regenerated.
- A bypass push (the API, `--no-verify`) that re-adds an already-public value passes the backstop, and exposes nothing new. A new scanner rule that hits old fork commits turns the backstop red until the baseline is regenerated in an approved PR.
