# Admin Center

<sub>Accounts and admin &middot; [All features](README.md)</sub>

Stock Omnigent manages the server on its Settings pages: harnesses, AI accounts, members and global policies. The fork adds an Admin Center, a page of its own extension built on Omnigent's extension API, so the core app is unchanged. It puts the release, deploys, the host, every account's limits and cloud spend on one board, and Settings > Global Policies gains an Edit button.

## One board for the server

<p align="center"><img src="../media/admin-board.webp" alt="One board for the server"></p>

The Admin Center opens on a board of cards under four headings, Ship, Box, Cloud and Accounts, the same four as the status pills below. Ship holds Deploys, Git repos and Social; Box holds Box health and Home security; Cloud holds Compute, Databricks credit, Azure spend, Key Vault and Decision model; Accounts holds Accounts and Spend. Each card reads its own source and draws its own empty or error state, so one missing integration never blanks the page. On a phone each card folds to one line that still shows its state: the title over a one-line note, about 56 px tall (2026-11-07), with runs of folded cards sitting two by two (an odd last card stays full width); Social's pill and pop-out and Box's host chip hide while folded. The board is for admins: anyone else signed in sees one line saying so, apart from a box admin, who sees Box health (below). The server enforces it too, so a non-admin's own calls for the host, secrets, Fabric and Databricks answer admin only, and the limits they can read are shared logins and their own sessions.

**Where:** Admin Center in the sidebar, between Inbox and Session Dashboard.<br>
**Built from:** [`packages/ae_omni_extension`](../../packages/ae_omni_extension); [`packages/ae_omni_policies`](../../packages/ae_omni_policies)

## Status pills

<p align="center"><img src="../media/admin-overview.jpg" alt="Status pills"></p>

Four pills in one row under the title say whether anything other than Needs you is wrong. Since 2026-11-06 they replace ten status tiles that wrapped to four rows above Needs you; four pills read at a glance and the cards below still hold the detail.

- **Ship:** Release, Deploy hold and Git repos.
- **Box:** Box health, the host, the secrets on the box and Home security.
- **Cloud:** Fabric, Databricks, Azure spend, Key Vault and the Decision model.
- **Accounts:** the Claude accounts, the Spend card's presets and families.

A pill takes the worst health of its members, and a group none of whose members is set up is not drawn. Green is quiet. Amber (needs a look) and red (a problem) tint the whole pill and show a small number at its right edge (how many members are not ok; a screen reader hears "2 to check" or "1 problem"). Under the name is one line of short phrases, never the longer notes: the members with a problem first, then the ones that need a look (both bold), then the ones that are fine, with repeated text dropped. The notes stay in the hover list and the screen-reader label. Hover a pill, or tab to it, to see every member with its value and note; the same list is the pill's screen-reader label. Click or press a pill to go to its group: on a phone it scrolls to the group's heading and opens its first card; on the packed board it scrolls to the group's first card, focuses its header and rings every card of the group for about 1.6 seconds. The Deploy hold's time-left bar sits inside the Ship pill. On a narrow page the pills sit two by two, and they stay on a phone.

The header also carries one sentence from the Needs you counts: "2 urgent, 3 to review.", "1 to review." or "Nothing needs you.", with " Everything else is fine." only when every group has reported, every pill is green and no source failed to read, and " Some sources could not be read." when one did. If the newest read failed it shows the last counts and " Last answer." instead of claiming nothing needs you. It says nothing until the Needs you list has been read, and the box-only view never says everything else is fine. Pill hover popovers show only where a pointer can hover; on a phone a tap scrolls to the card.

**Where:** The top of the Admin Center.<br>
**Built from:** [`packages/ae_omni_extension`](../../packages/ae_omni_extension)

## Drag cards to rearrange

<p align="center"><img src="../media/admin-drag.webp" alt="Drag cards to rearrange"></p>

Each card header has a grip. On two or more columns, drag a card to any column or position on the board, or focus the grip and use the arrow keys; the arrow keys stop at the board's edge. Needs you has no grip and stays first in column 1, and nothing drops above it. The layout is saved once for the whole board and per column count (2, 3 and 4) under the storage key `board.packed`, and Reset layout brings the packed default back. A layout saved before 2026-11-07 (per group, key `board.layout`) is no longer read, so the board packs itself until you drag again; the old value is left in storage.

Since 2026-11-07 (packed board) the group sections are gone from two columns up. The board is `n` column stacks side by side: Needs you is the first tile of column 1, then each card, in Ship, Box, Cloud, Accounts order, goes into the column with the least guessed height so far (ties go left; `CARD_HEIGHT_GUESS` and `NEEDS_YOU_HEIGHT_GUESS` in `boardLayout.ts`, never what is rendered, so placement depends only on the card set and the column count and never moves after render). Every card carries a small group tag (SHIP, BOX, CLOUD, ACCOUNTS) above its header. A fourth column starts at a page width of 1,720 px, so a 16:9 screen gets four columns and a 4:3 one gets three. Opening a big Needs you source lengthens column 1 only, and a gap can show at the bottom of the other columns. The phone (one column, page under 520 px) is unchanged: four group sections, with Needs you above the board. The four status boxes are one height.

**Where:** The grip at the right of any card header, on two, three or four columns.<br>
**Built from:** [`packages/ae_omni_extension`](../../packages/ae_omni_extension)

## Cards: turn a card on or off, or hide it

Added 2026-11-07. Until then every card was set up only by server environment variables, with no way to switch one off, and the Social card carried one owner's channels into every install. The **Cards** button in the page header (and the gear in each card's header) opens a panel from the right: each card with a state chip (On, Off, Needs setup, Hidden for you), an eye, a switch, and a Setup fold that lists each field, what it is for, whether the server's environment sets it, and the exact variable name to set with a copy button. It never shows a value.

- **The switch** turns a card on or off for everyone on the server. Only an OmniGent admin can flip it, and only from the Admin Center page in a browser: a bearer call, a device-login or refreshed sign-in token, or a call without the page's headers is refused. Since 2026-11-08 ([issue 506](https://github.com/analyticendeavors/omnigent-ae/issues/506)) the page's sign-in must also carry a browser proof: a second cookie (`__Host-ae_browser_proof`, `ae_browser_proof` on plain HTTP) that the server sets only on a browser sign-in response, holding an HMAC of the exact session cookie. A token a command-line sign-in stored, a refresh grant, a bootstrap token, a runner token or a magic-link session has no proof, so replaying it as the cookie is refused. One sign-out and sign-in per browser after the deploy sets the cookie. The iOS app (0.3.1) holds a sign-in token with no proof, so the switch is refused there and a browser does it. The desktop app also has no proof, but since 2026-11-09 its own sign-in counts (see "The desktop app" below). A browser signed in through a magic link (accounts mode) never gets a proof, so it needs a password sign-in for these writes. Each switch is logged with who did it, and an off card shows "Turned off by <login> on <date>". Two admins changing it at once never overwrite each other: the later one is told it changed elsewhere and sees the saved state.
- **The eye** ("Hide for me") hides a card for you only. It is kept in your browser's storage and changes nothing on the server.
- **What off does:** the card leaves the board, its tiles leave the status pills, its lines leave Needs you, and the server stops its background reads (no Git refresh while Git is off). Its own read routes answer `{"off": true}` at once with no outside call. A key that is present keeps its Box health row and its expiry, so turning a card off never hides an expiring key; only the "missing" rows of keys that only switched-off cards use go.
- **What off does not stop:** Deploys, Accounts, Spend, Decision model and Box health keep answering their server routes, because deploy scripts, sessions, hosts and the MCP tool list depend on them. For those, off means the board, the pill and Needs you only.
- **Secrets are not on this screen.** Each key stays in the server's environment; the panel only says whether it is set and which variable to set.
- **Where the state lives:** `/data/ae-admin-cards.json` (`AE_ADMIN_CARDS_FILE` moves it; an empty value keeps it in memory). A damaged file reads as "unknown": the cards show their defaults, the switches are disabled with a hint, and the file is never overwritten.
- **The desktop app (2026-11-09, follow-up to [PR 509](https://github.com/analyticendeavors/omnigent-ae/pull/509)).** The desktop app signs in through `POST /auth/native-token` and installs its own cookie, so it can never hold the browser proof, and its renewals carry a login grant. `desktop_signin.py` records that one sign-in: when upstream's own `native_token` endpoint answers 200 for a loopback sign-in (form body under 16 KiB with exactly one `redirect_uri`, an `http://127.0.0.1` or `http://[::1]` address; the iOS private-use redirect is not recorded), it stores keyed hashes (HMAC under a key derived from the cookie secret) of the session token and of the user, the id of the login grant issued in the same answer (an identifier with no authority; it is also kept as a keyed hash), the token's expiry and a created time. It records only when the answer carries a refresh token that maps to a login grant of that same user; otherwise nothing is recorded (and with no grant store reachable at startup nothing is installed), so the desktop is refused. The gate accepts that exact token until it expires, and any renewal through `/oauth/token` of that grant (`act.client_id` is the login grant client, no `scope`), and in both cases only while the grant is live in the grant store (exists, not revoked, inside its lifetime), asked on every gated write with no cache. So signing out in the app ends the first token and every renewal at once (until 2026-11-09 the first token would have outlived sign-out until its own expiry, up to 720 hours). Behind a configured base path the endpoint is recognised by the exact mounted path, never a suffix, and a 200 from a path ending in `/auth/native-token` that was not recorded is logged once. A command-line ticket sign-in, a command-line refresh-grant renewal, a bootstrap token, a runner token, a device grant or a client-credentials token is never recorded and stays refused. The record is `/data/ae-desktop-signins.json` (`AE_DESKTOP_SIGNINS_FILE` moves it; empty keeps it in memory), mode 0600, no token or name in it, at most 8 entries per user, pruned when both the token and the grant are out of date. A missing or damaged file reads as empty and a failed write is logged and refused later, so the desktop fails closed. OIDC mode only (accounts mode has no native sign-in). After the deploy, sign out and in once in the desktop app. Optional `AE_DESKTOP_SIGNIN_REAUTH=1` (off; leave it off until the identity provider sends the `auth_time` claim, or every native sign-in is refused) makes the desktop's sign-in page ask for a fresh password or passkey (only on the exact `/auth/login` path and only for a loopback redirect; an iOS redirect is untouched).
- **What stays open (2026-11-09):** an agent that reads the browser's own cookie store (both cookies sit there), or the desktop app's encrypted credential file and cookie jar (same user); an agent on the owner's PC that runs its own loopback native sign-in through the system browser with single sign-on, which is about as easy as `omnigent login`, so for an agent on the PC the gate is back at command-line strength (agents on the box cannot: their browser views are isolated and refuse loopback, and no browser there is signed in to the owner's account), and the re-authentication switch above raises that effort without closing it; an agent that drives the real browser through a sign-in and replays the code; a command-line ticket sign-in and a desktop sign-in by the same user in the same second, which mint the same token; `docker exec` on the box, rewriting `/data/ae-admin-cards.json` or reading the cookie secret from the container environment; cross-site scripting in the web UI; and admin writes that are not behind this gate, which stay reachable with a command-line token by design. In accounts mode the same check also guards `POST /auth/invite` and `POST /auth/users/{id}/reset`, so an admin's command-line token cannot mint an invite or reset a password to obtain a proof.

### Settings typed in the panel

Added 2026-11-07. A new install used to set a card up by editing `config/server.env` and restarting. The Setup fold now has an input for the plain, non-secret settings, one Save per card, and a Clear link on a saved value. Fields you can type: the Git lists (`AE_GIT_SWEEP_CONFIG`, `AE_GIT_SWEEP_WORKFLOW`, `AE_GIT_REPOS`, `AE_GIT_VIEW_ONLY`, `AE_GIT_KEEP_BRANCHES`), the Databricks credit (`AE_DATABRICKS_CREDIT_USD`, `_CADENCE`, `_START`, `_END`), the Azure subscription list (`AE_AZURE_COST_SUBSCRIPTIONS`, as `id=name`) and the Fabric price (`AE_FABRIC_USD_PER_CU_HOUR`).

- **The environment always wins.** A variable the server's environment sets (and does not leave blank) is used as it is, and the panel shows that field read only with "Set in the server's environment. Change it there." The panel's value is used only when the environment has none, so a server configured by hand changes nothing when it upgrades. The panel says where each field's value comes from: the environment, this panel ("Saved by <login> on <date>"), the code's default ("Default: 0.18") or nothing.
- **Where the values are kept:** in `/data/ae-admin-cards.json` beside the switches, under the same revision (two admins saving at once never overwrite each other) and with the same rule for a damaged file: saving is refused and the file is left alone. The card reads the new value on the next request; its cached answer is dropped when you save.
- **Why other fields stay in the environment:** a secret, a key or a signed link never goes through the panel. Neither does anything that decides where the server sends a credential (the GitHub, Databricks, decision-model and Fabric addresses, the Azure tenant and every client id): a saved value could otherwise point a server secret at another host. Anything a host relay or script reads (the Box health settings, the Key Vault name) says "Set on the host, in config/host.env", because the server cannot change what the host reads. The Social card's JSON settings, the preset-run and family-cost switches (read once at start) and the decision model's file and switch also stay in the environment.
- **Checks:** a list is comma separated, trimmed and de-duplicated (at most 50 items); a repository is `owner/repo`; a kept branch is `owner/repo:branch` with git's branch-name rules; the sweep config is `owner/repo:path` with no `..` and no leading `/`; a subscription is `<id>=<name>`; the credit and price are plain positive numbers; dates are `YYYY-MM-DD` and the credit start must not pass its end. No value is over 2,000 characters. A bad value is refused with the rule, never with the value echoed back, and the log line for a save names the card, the variables and the login, never a value.
- **Who may save:** the same people and path as the switch: an OmniGent admin, from the Admin Center page in a browser.
- **Prefix fields** (one variable per account or capacity, such as `AE_GIT_TOKEN_<OWNER>`) show a count, "Set for 3 accounts", when one or more exist and "Not set" when none do; never the names or values.

**Where:** the Cards button in the page header; the gear on each card; "Cards settings" under the board.<br>
**Built from:** [`packages/ae_omni_extension`](../../packages/ae_omni_extension); [`packages/ae_omni_policies`](../../packages/ae_omni_policies) (`admin_cards.py`, `card_config.py`)

## Not set up on this server

An integration the server says is not configured leaves the board instead of showing an empty card, and the board's last line names it. That one line also names the cards that are turned off or hidden for you, each part only when it has cards: "Turned off: Social (by <login>, Nov 7). Hidden for you: Spend. Not set up on this server: Key Vault." A "Cards settings" button at its end opens the Cards panel, which shows how to set each one up. A group with no card left draws no heading, and the integration's tile leaves its status pill (a pill with nothing left is hidden). Only a plain "not configured" answer counts. An error, an admins-only answer or a read still in progress keeps the card, and a Key Vault that is not configured is never amber (a box that has not reported is). Deploys, Box health, Accounts, Spend, Social and the page header are never dropped for being not set up (they can still be switched off or hidden, see "Cards" above). Each integration, and the setting that turns it on:

- **Fabric:** `AE_FABRIC_WAKE_URL_<NAME>` (with `AE_FABRIC_SUSPEND_KEY_<NAME>` for Pause, and `AE_FABRIC_CAPACITIES_URL` and `AE_FABRIC_CAPACITIES_KEY` to list every capacity). Compute leaves the board only when Databricks is also not set up.
- **Databricks:** `AE_DATABRICKS_HOST`, `AE_DATABRICKS_CLIENT_ID` and `AE_DATABRICKS_CLIENT_SECRET`. Databricks credit leaves with it; with Databricks set up but no credit amount and dates, the credit card stays and says so.
- **Azure spend:** `AE_AZURE_COST_SUBSCRIPTIONS`, `AE_AZURE_COST_TENANT_ID`, `AE_AZURE_COST_CLIENT_ID` and `AE_AZURE_COST_CLIENT_SECRET`.
- **Key Vault:** `AE_VAULT_NAME`.
- **Decision model:** an endpoint, a key and a non-empty denylist file (`AE_DECISION_ENDPOINT`, `AE_DECISION_API_KEY`, `AE_DECISION_DENYLIST_FILE`). The footer names it "Decision model". Once those are set the card stays, and `AE_DECISION_ENABLED=1` switches it on.
- **Git repos:** a Dependency Sweep config (`AE_GIT_SWEEP_CONFIG`) or `AE_GIT_REPOS`.
- **Home security:** the home app's address (`AE_HOME_SECURITY_URL`). Without it the card leaves the board and its route answers off.

The box-admin view (one Box health card) has no headings and no such line.

## Hold deploys

<p align="center"><img src="../media/admin-deploy-hold.webp" alt="Hold deploys"></p>

A deploy restarts the server and ends every running turn. Hold 1 h, 2 h or 3 h pauses the box's automatic deploys; a ring counts down, the card says when the hold ends and who set it, and the hold ends on its own or with Resume. The card also shows the running release and any newer one queued, and how many busy sessions it waits on. The hold is admin only and needs no configuration (the server keeps it in its data volume, and `deploy/auto-update.sh` reads it); the newest release needs `AE_GITHUB_TOKEN`, and without it the card says the newest release is unknown.

**Where:** The Deploys card.<br>

## Box health

<p align="center"><img src="../media/admin-host.webp" alt="Box health"></p>

The host card says whether the box's host is connected, and when it is not, how far the sign-in relink helper has got and lets an admin request a new link (the relink ends every live session, so it is admin only, and a non-admin never sees the button). Server secrets lists every key the server expects by what it turns on, never by value, and flags a missing required one. Each key is a row with its Key Vault name, when the vault says it expires (amber inside 60 days, red once past, "no expiry set" otherwise), when it last changed, and an Edit link (the Azure portal page) and a Rotate link (the system that issues the value, with the account it opens in a hint). The dates come from a daily timer on the box, because the server never reads the vault; the card says when that reading is missing or over 36 hours old (`deploy/README.md`, Secret expiry dates). The sign-in and task-store secrets count as required only when OIDC sign-in or the task store is set up. The relink status comes from `deploy/host-relink.sh`; without it the card shows only the connection.

Since 2026-10-23 the secrets block is "Secrets on this box" and starts collapsed: the counts, then a chip for each key that needs you (missing, expired, expiring inside 60 days, or refused on the server's last call), or one green line naming the next expiry. Show keys opens the rows, and the page remembers it. The host's Claude token is a row too, tagged host, once the box's daily check has reported it. Each server key also says when the server's own calls last worked with it ("worked 2:07 PM") or were refused ("failed: 401 at 1:50 PM"); that is kept in memory, so it counts from the last server start. A refused required key turns the block red, a refused optional one amber.

Since 2026-10-28 the card opens with a box monitor. On 2026-10-28 the box's `/tmp` (a 62 GB RAM tmpfs capped at 1,048,576 inodes) ran out of inodes because nothing cleaned Claude Code's per-session temp folders, and every Claude Code Bash call failed for about 15 minutes. A timer on the box (`ae-omnigent-box-health.timer`, every five minutes) now posts heat, CPU, memory, storage and bloat, and the card shows five lines (Heat, CPU, Memory, Storage, Bloat) under a "This box" header with a Details button, plus up to three Needs you lines, worst first. Amber and red are deliberate: one hot CPU reading stays green (boost bursts to 91C are normal), but every reading for 15 minutes at 90C or more turns it amber; a mount is judged on the worse of its space and its inodes. Details opens a dialog with the tables, a day of heat sparklines, and every setting with a one-line hint.

The monitor covers both box users, the owner and the second box user, and names neither one's work. Rows are per user and carry counts, sizes and ages only: stale Claude temp folders (older than two days, kept alive by any live session, which the box's temp guard protects and the card counts), leftovers at the top of `/tmp` by pattern, worktrees (counted and sized, never listed), and the second box user's container, measured through fixed read-only commands. A folder of another user that the box user cannot read shows as "not readable" with its age. Nothing posted holds a folder, project, session, branch, worktree or file name, and a test pins that. The same goes for the things around them: a mount is named only from a short list (`/`, `/tmp`, `/boot`, `/boot/efi`, `/home`, `/var`, `/secure`, `/run`, `/dev/shm`) and any other is "other mount N" with its numbers; a failed systemd unit is named only when it is an `ae-` unit (with any `@instance` dropped), one of systemd's own or Docker's, and the rest are counted ("2 other"); a folder whose size is reported is shown by the label its setting gave it, never its path.

Who sees it: OmniGent admins see every card. A box admin (a login in the server's `AE_BOX_ADMINS`, for the second box user) sees only this card and its tile, and nothing else is requested for them. Anyone else sees one line saying the Admin Center is for admins. Reading is all a box admin can do; only an OmniGent admin's login can post a reading.

Since 2026-10-29 a box admin can clean up from the card. Details has a Cleanup section with one button per cleanup the box offers now, and a Needs you line that a cleanup clears has a Clean up button that opens the same confirm step. The confirm text says whose items, how many and how big, and what is left alone ("This cannot be undone"). Four cleanups exist: a user's Claude temp folders older than two days, the old test leftovers at the top of `/tmp` (by fixed name patterns, such as `sec-appr-*`, where a six-character suffix must hold a digit or a capital letter after the first character so a name a person chose never matches; since 2026-11-05 this one also runs by itself every six hours from `ae-tmp-litter-sweep.timer`, `deploy/README.md`), review checkouts in `/tmp` with no uncommitted changes, and Docker's dangling images and build cache older than two days. Pressing the button only queues the request; the box's relay picks it up within five minutes, runs it as its own user (never root, never `~/worktrees`, never a running session's folder), and posts a result the card shows ("Removed 268 folders, freed 9.8 GB"). The card shows who ran it only to OmniGent admins; other box admins see "a box admin". One request exists at a time, can be cancelled until the box takes it, and the card says so if the box never picks it up. Another user's host-side folders are not offered, because only the box's own daily rule can remove them. Each mapped container also ages its own two-day-old temp folders every hour, and Details says how many; before each removal the relay checks, inside the container, that nothing in the folder changed lately and that no process works in it or names its session on a command line, and removes nothing when a check cannot finish. One run removes at most 5,000 items, oldest first, so a larger offer reads "Remove up to 5,000 of 14k items" and its confirm says to press again for the rest. Every confirm says the box runs it within 5 minutes; a run whose fresh plan is larger than what you confirmed removes only that many of the oldest items (judged by the newest file inside each) and says how many more aged since (they stay for the next run), a Remove button that is locked says why in a line beside it, and a request it has not taken in 15 minutes expires. `AE_BOX_HEALTH_CLEANUP=off` in `host.env` hides every button and stops the aging. No folder, project, session, repository, branch or file name appears in the confirm text, the result, the card or the server log.

Since 2026-10-29 the card is laid out differently; what it shows has not changed. The host's live status (a dot, its name and a state pill) sits in the card's header, between the title and "Updated", and drops to a second header line under the title on a phone and on any card under 480 px (the 295 px three-column card and the 205 px two-column card). It stays visible when a phone card is folded, and it is the same status the host's tile reads, redrawn on every poll. Under the header a status line gives the worst state as a pill ("3 need you", "OK" or "No reading", colored by the box's tone), when the box was read and Details. The five readings are small tiles (five across from 600 px of card, two across below that, a plain list at 260 px and under); a tile that is amber or red is tinted. A "Needs you" panel holds each need with its Clean up button at the right of its row, and the queued or running cleanup request is the panel's last row, with a clock icon and its Cancel request button. The host's own block (its facts, notices and the reconnect button) appears under the status line only when the host has something to say, which is when it is not connected. Secrets take the full width as one block. Every nested surface uses the inner color and its border, as the other cards do ([#351](https://github.com/analyticendeavors/omnigent-ae/pull/351)), buttons on those surfaces take a slightly lighter step so they read against them, and the queued request's stripe has a color (before, it had none and showed almost nothing in dark). Each control keeps its tooltip or hint, and touch targets stay 44 px on a touch screen and on a narrow one.

Since 2026-11-06 the card has one rule for how far the cleanup scan can be believed. When the hourly scan stopped counting at its file or time limit, the Bloat line turns amber with one need, "Temp folder count stopped early": counts are at least what is shown, and folders past the limit are not counted or cleaned. When the scan is older than three of its own intervals, the need is "Cleanup scan is late". Both come from the same list as the Box pill, so the card, its tile, the pill and the Needs you list agree. "Could not be read" now means a real read failure only: a stale reading, a failed fast part, a scan that was cut short or failed in a part, or no slow scan at all.

Since 2026-11-06 each Claude chat temp folder gets its own share of the scan's entry cap (`AE_BOX_HEALTH_GROUP_MAX_ENTRIES`, 100,000 by default), in the hourly scan and in the hourly auto-clean. On 2026-11-06 one finished chat's folder held 1.28 million entries and spent the whole cap, so every folder after it was never counted and the big one stayed unproven. Now a folder past its share is the only one that reads "at least" (its age is unproven, so it is never called stale and never cleaned), and the scan goes on with the next folder; the whole scan still stops at `AE_BOX_HEALTH_WALK_MAX_ENTRIES` and the seconds cap. The same share applies to a pytest run. The container's listing is one fixed command stream and keeps the single cap.

Since 2026-11-06 the host block and the secrets block each end with a "N in Needs you" line that opens the panel filtered to Box host or Secrets on box.

**Where:** The Box health card.<br>

## Key Vault

Every secret in both Key Vaults (the main vault and the website's `kv-example-web`), by name. A switch picks the vault; four numbers count the expired ones, those expiring inside 60 days, those with no expiry set and those unchanged for 180 days or more; Needs you lists the few worth a look, worst first, including any secret whose two copies were changed apart and so needs rotating in both vaults. ## Git repos

One card for every repository across several GitHub accounts, so a backlog cleanup reads from one place instead of dozens of `gh` queries. It sorts everything by who moves next. Four numbers come first (ready to merge, alerts to fix, old branches, waiting on GitHub), then Needs you, the few things only you can decide, worst first: an account or repo that cannot be read, a late or failed Dependency Sweep, alerts still vulnerable on the default branch, a failing or conflicting pull request, one ready to merge, alerts GitHub has left open more than a day after the fix landed, and branches with no pull request whose last commit is over two weeks old. A pull request whose only failed checks are cancelled duplicates of a check that passed is read by its other checks (pending while one still runs, passing once all pass), so it raises no Fix item and its pill is not red. Everything else (alerts GitHub has not cleared yet, checks still running, the sweep's own Dependabot pull requests, drafts, recent branches, branches marked as kept, view-only repos) is one line each under Not yours to move. Show all opens every repo, folded, with a search box and chips for PRs, alerts, branches and view-only repos.

Alerts are split by what the default branch really installs: the server reads each alert's lockfile (npm `package-lock.json`, pinned pip `requirements.txt`) and compares the installed version to the vulnerable range. An alert whose lockfile cannot be read counts as needing a fix, so nothing hides. Read only: every row links to GitHub. Repos named view only are shown and left out of every count. Admins only.

The repo list comes from a Dependency Sweep config (`AE_GIT_SWEEP_CONFIG`, `owner/repo:path`) plus `AE_GIT_REPOS` and `AE_GIT_VIEW_ONLY`; `AE_GIT_KEEP_BRANCHES` names branches kept on purpose. Each account reads with its own read-only token, `AE_GIT_TOKEN_<OWNER>`, falling back to `AE_GITHUB_TOKEN`; an account with neither shows as not connected (`deploy/README.md`, The Git repos card's tokens).

**Where:** The Git repos card; its tile says how many things need you and how many alerts need a fix.<br>

## Git: company and personal lists

Added 2026-11-08 (card setup part 3). Until now the Git card read one list, the company's, with tokens set only in the server's environment. Each admin can now also keep a **personal list** of their own repos under their own GitHub accounts, and the company tokens can be typed in the Cards panel instead of the environment. In the Cards panel, open Git and its Setup fold.

- **Company repos.** Every admin sees these and admins edit them. A company token is read in this order: `AE_GIT_TOKEN_<OWNER>` in the environment, then the token saved here, then the server-wide `AE_GITHUB_TOKEN`. The environment always wins over a saved token, and `AE_GITHUB_TOKEN` itself stays in the environment only.
- **My GitHub accounts.** Only you see these. "Connect another account" takes a token, Check asks GitHub who it belongs to and which repos it can read ("Signed in as octo-user. 9 repos visible."), you tick the repos you want, and "Save N repos" keeps them. Replace pastes a new token for an account; Remove deletes the token and that account's repos. The list has at most 30 repos per person.
- **Who may have a personal list.** OmniGent admins only (decided 2026-11-07). Every route here is admin only, and every save is browser only, like the switch (the same gate, with the browser proof or the desktop app's recorded sign-in, and the same list of what stays open). Giving it to every user is a later step; personal Needs you items already have their own source (`git-mine`) so that step stays safe.
- **The token.** A fine-grained GitHub token (starts with `github_pat_`), read only: Metadata, Contents, Pull requests, Dependabot alerts and Actions. The screen links to GitHub's page for making one. The server only reads with it, and it asks GitHub (`GET https://api.github.com/user`, a fixed address, never one from the environment) who the token belongs to and when it expires. An expiry within 14 days shows as a warning. Company tokens typed here follow the same rule; a token set in the environment can still be any kind.
- **Where tokens live.** In `/data/ae-card-secrets.json` (`AE_CARD_SECRETS_FILE` moves it), mode 0600, each token encrypted with Fernet under `AE_CARD_SECRETS_KEY` (a comma separated list rotates: the first key encrypts, any key decrypts, and the first load re-encrypts old records). Without that key the screen says "Set AE_CARD_SECRETS_KEY in the server's environment to save tokens here." and nothing can be saved; tokens in the environment keep working. A token is write only: no route, list, log line or error returns it, and the token you type lives only in the password box until the save answers, then it is wiped. A person's repo list is in `/data/ae-git-personal.json` (`AE_GIT_PERSONAL_FILE`).
- **The reading rule.** A company repo is read only with a company token. A personal repo is read only with that person's own token for that repo's account, never with a company token, never with `AE_GITHUB_TOKEN`, never with another person's token. The cache and the memory of failures are kept per person, so one admin's personal answer is never shown to another. A repo in both lists shows once, under Company, in the All view.
- **The card.** The Git card has a Company, Mine, All switch (All by default, remembered per viewer). A personal row carries a "Mine" tag.
- **Needs you.** Personal items form their own group, "My Git repos", shown only to their owner, with item ids that carry the owner's login. They offer **Open on GitHub and Dismiss only**: Fix chat, Review and Merge act as the box's own GitHub login, so the server refuses them on a personal item, Review all leaves them out, and the page never draws those buttons for them. The background tidy of dismissals never marks a personal item as gone (it reads nobody's personal list), so a dismissed personal item is not cleaned up when its cause is fixed: it comes back if it gets worse and otherwise expires after 14 days.
- **Background reads.** The cleanup pass refreshes the company repos as before, plus the personal lists of admins who opened the Git card in the last 7 days, at most once every 15 minutes each, at most 20 people. Nothing is read while the Git card is off.
- **Offboarding.** Other admins appear only as a count ("Other users: 1 has 1 personal account connected") with "Clear their tokens" behind a confirm; you never see their repos, accounts or tokens. When a login is no longer in OmniGent's user list, its tokens and repos are cleared at the next check; a login that is no longer an admin is skipped and read for nobody. An answer from OmniGent that lists no users never deletes anything.
- **What stays open.** Anyone who can read the server process or its environment can read every saved token, as they can read the environment today. A fine-grained token's write permissions cannot be checked through GitHub's API; the server never writes with it, but the owner should make it read only. The browser-only gate now refuses a token copied from `omnigent login` into the cookie slot ([issue 506](https://github.com/analyticendeavors/omnigent-ae/issues/506), 2026-11-08); the other open items are listed under Cards, The switch.

## Social card

Since 2026-11-07 the card is hidden unless the server sets `AE_PRIVATE_CARDS=social`: without it the card is off, absent from the Cards panel and its routes answer `{"off": true}`. Its channel ids, promoted tools and channel names come from `AE_SOCIAL_CHANNEL_IDS`, `AE_SOCIAL_TOOLS` and `AE_SOCIAL_CHANNEL_NAMES` (JSON), not from code; `AE_SOCIAL_TOOLS` seeds only a fresh state, and tools already saved stay. Built 2026-11-06 so promoting each video does not depend on remembering to. Reid publishes YouTube videos, Shorts and livestreams on two channels (AE and HC), must promote each on LinkedIn (long videos also get a YouTube Community post), promote three of his own tools and write a weekly expert post. The card plans those posts from the real uploads, shows the next three, and makes each one Copy, Open, Mark posted. Admins only.

**What it shows.** A header pill ("N overdue", "N due today", "On track" or "Behind"), three score boxes, warning lines, "Up next" (the next three open posts, overdue first) and a footer with the on-time rate and how old the YouTube reading is. The first row has Copy (the draft to the clipboard), Open (copies, then opens LinkedIn's share box with the text, or the channel's Community tab) and Posted. Both Open links are unverified against the live sites. Since part 3 (2026-11-06) Open is never disabled: on a post with no draft it opens the full view's editor on that post, with its starter text, and Copy and Open copy inside the tap (see "The Social card on a phone").

**The score, in the words the card uses.**
- **This week:** LinkedIn posts you marked posted since Monday, against your weekly target (3). "On pace" means you are not behind for the day of the week: posted is at least the target times the day number (Monday is 1) over 7, rounded down.
- **Promoted, 30 d:** videos and Shorts that went public in the last 30 days and got every planned post. A Short post you chose to skip still counts as done, and a Short is not counted as missed until three days after it went public.
- **Streak:** full weeks in a row that hit the LinkedIn target. The current week joins once it hits (the first week never counts). The server keeps a per-week count of marked LinkedIn posts for 104 weeks, so the streak outlives the 63 days the posts themselves are kept; the best streak is stored. Weeks wholly before the first YouTube read neither count nor break it.
- **On time:** posts marked posted within a day of their due time, last 30 days.

**What gets planned.** A LinkedIn post for each long video when it goes public, plus a Community post; a LinkedIn post for each Short (optional); a LinkedIn post the day before each livestream at the alarm time; one tool post on Fridays, rotating through the active tools (oldest last use first); one expert post a week on Wednesdays, and more expert posts on Tuesday, Thursday, Monday and Friday when a week would otherwise miss the target. Slots are planned 35 days ahead and kept 63 days back, but nothing is planned or scored for an upload that went public before the first YouTube read (the start line), so day one does not show a backlog as missed. Skipping a post ends that obligation: the planner does not add a replacement. When the rules or tools change, unfrozen future tool and expert slots follow them. A slot that is posted, skipped, drafted or moved is never changed by the planner. The rules (time zone, alarm time 09:00, target, gap days) and tools are stored with the state and change through `POST /v1/ae/social/rules` and `/tools`.

**Warnings.** "HC channel: nothing scheduled in the next 7 days", "AE read failed: <error>" and "YouTube read 7 h ago" (stale after 6 hours). A channel whose read failed keeps its previous uploads.

**How it runs.** The server never holds the YouTube login; a two-hourly timer on the box runs `python -m ae_omni_policies.social_relay`, which runs the youtube-video-publish skill's lister and posts the uploads to `POST /v1/ae/social/uploads` (`deploy/README.md`, Social card). The state is `/data/ae-social.json` (`AE_SOCIAL_FILE`). Every route is admin only, writes use POST with the id in the JSON body, and `GET /v1/ae/social` stays under the bridge's 32,768-character cap (`truncated` says when slots were cut). `GET /social/week` and `POST /social/drafts` serve the weekly drafting run; a draft Reid edited is never overwritten.

**Limits.** Nothing can read LinkedIn, so "posted" is only what you mark (Reopen undoes a mis-click), and YouTube has no Community-post API, so those posts are manual too. Both are why the card copies and opens instead of posting.

**Posting from a phone (core patches 0303 to 0306, 2026-11-07).** Reid's first iPhone test found that the compact card's Open said "Copied, opened" but the LinkedIn app never opened and a paste in LinkedIn gave nothing. Two causes. (1) `copyText` awaited `navigator.clipboard.writeText` first; the sandboxed frame has no clipboard grant, so it always rejected, and the working fallback (a hidden textarea and `execCommand`) ran only after Open had sent `openExternal` and the app had switched away. `copyText` (`lot.ts`) now does the selection copy synchronously first and tries the clipboard API only if that returned false. (2) The iPhone Home Screen app opens an outside link in Safari's in-app view, and iOS never hands such a link to the LinkedIn app. The fix is the phone's own share sheet:

- **`navigation.share` (patch `0303`).** A host service next to `navigation.openExternal`, with the same `navigation` permission. The host calls `navigator.share` itself, from the same tap, so the frame's sandbox and CSP are unchanged. Params: `text` (at most 3,000 code points), `title` (at most 200) and `files` (one jpeg or png File or Blob of at most 5 MB). When the sheet cannot take files it shares the text and answers `{shared: true, files_dropped: true}`. Errors: `ShareUnavailable` (no `navigator.share`), `ShareCancelled` (the sheet was closed) and `ShareFailed`. The host always wraps the image in a new File named `image.jpg` or `image.png`, so an extension cannot choose the file name, and the RPC check refuses a Blob over 5 MB or of another type. `navigation.share({probe: true})` answers `{available}` and shares nothing. Every host call times out at 10 s except this one, which gets 10 minutes (the sheet stays open that long); patch `0304`. The RPC budget refuses a Blob and any message over 64 KB, so the patch takes one Blob out of a `navigation.share` request's `files` before the budget check.
- **Share to LinkedIn.** On a touch device (`(pointer: coarse)`) the editor's primary LinkedIn button reads "Share to LinkedIn", and the compact card's Open on a LinkedIn post takes the same path (`socialShare.ts`). In the tap, before any `await`: copy, remember the tap, call the share sheet with the text and the picture as a File named after the post (if it has loaded; the tap never waits for it). A finished share asks "Did you post it?" at once; a closed sheet forgets the tap and shows nothing; a share the host stopped waiting for (`Timeout`) is an unknown outcome, so the post stays remembered, the banner asks, and no error shows. Whether the browser has a share sheet is probed once when the full view opens and cached; the tap chooses the sheet or the composer link from that answer, synchronously (a link opened after a failed share runs outside the tap, where iOS can refuse it). If a real share still fails with `ShareUnavailable`, the note says the draft is copied and to paste it; it does not open a link late. While the picture loads, the Share button reads "Loading image..." and is disabled for at most 8 seconds; if the picture fails or is late the button works and says "The image could not load; this shares the text only." (on the compact card, Open opens the editor while the picture is still loading). A desktop keeps "Post on LinkedIn" and the web composer, and a Community post keeps copy plus the Posts tab.
- **The picture.** The frame can show only `data:` and `blob:` images and cannot fetch, so the server fetches it: `GET /v1/ae/social/visual/{slot}/{part}` (admin only, `social_visual.py`) answers `{type, size, parts, part, data}` with at most 24,000 base64 characters a part, so each answer stays under the bridge's 32,768-character cap. A slot row carries `visual: {kind: "thumbnail", key: <video id>}` for an upload that is public now (or past its go-public time), `visual_note` ("The thumbnail shows once the video is public.") for one that is not, and `visual: {kind: "tool", key: <image link>}` for a tool with an `image` (the card caches a picture by slot and `key`, so a changed tool image is fetched again); an expert post has none. The server fetches only `https://i.ytimg.com/vi/<id>/maxresdefault.jpg` (then `hqdefault.jpg` on a 404) and a tool's image on opengraph.githubassets.com or a host in `AE_SOCIAL_IMAGE_HOSTS`, follows a redirect only within those hosts, keeps at most 3 MB of image/jpeg or image/png, and caches 20 pictures for an hour. Each tool has an optional `image` link (https, at most 300 characters, one of the two hosts; the Settings fold has an "Image link" field with a hint); diagram and skins default to the site card and omnigent to its GitHub social preview. The editor loads the picture when it opens and shows it in a Visual row above the Post bar.
- **Bold line 1.** LinkedIn shows plain text, so line 1 can be set in Unicode's Mathematical Sans-Serif Bold letters (`boldFirstLine` in `socialWords.ts`: A to Z, a to z, 0 to 9, line 1 only; a link, #hashtag or @mention on it never, because LinkedIn will not link a bold one). The editor's "Bold line 1" chip (on by default for a LinkedIn starter text) rewrites line 1 either way. The counter counts code points, and the composer link percent-encodes the bold letters as usual (the host's allowlist decodes and counts code points).
- **One meta line.** Under the title, the due time, channel, count and the Bold chip share one line; the due text truncates on a narrow phone, never the count or the chip. A short tag ("Starter text", whose tooltip is "Starter text, edit before posting"; or "Unsaved edits", "Draft by ...") joins the line when it fits and wraps under it when it does not. On a phone the text box grows to fill the sheet, with the Visual row right above the pinned Post bar.
- **Redraft feed.** `GET /v1/ae/social/week-redraft` is `/social/week` plus the open posts whose draft is the weekly run's own and unedited (`redraft: true`); `social_relay week --redraft` prints it. `POST /social/drafts` still overwrites only an unedited auto draft. The redraft feed's `recent_topics` leaves out the topics of the slots being redrafted.

In the chart, weeks before it show as a muted "before start" note, not as empty bars.

## Spend card: families

The Families tab ranks each session family's spend over the same 7 or 30 days: a lead plus every session it started (builders, reviewers, Codex reviewers) and its native subagents, so a runaway family shows at a glance. Each family is one line (its title, a host chip, a bar against the biggest family and the number) in a scrolling list with a filter above it; open a line for its role chips (the lead's chip reads "lead incl. subagents"), counts, today's spend, the lead's context size and how many times its Claude process restarted. "Show cost as" (tokens or dollars, tokens by default) picks which number leads and the ranking; the other is on hover. Two flag amounts, each with its unit inside its box: "Flag a family over this many tokens a day" (5M by default, counting input plus output and leaving cache reads out, so a long chat re-reading its context does not trip it; it reads 5M, 500K, 1B or 5,000,000, up to 1B) and the same in dollars ($25 by default; it reads 25, $25, 25.50 or 1,000, up to $100,000). Each shows a Saved tick or an error in place, and 0 turns it off. A family whose spend today passes either amount raises a Needs you line naming it and puts a warning pill on the Families tab. All three settings are saved per user with the roles list. An OmniGent admin sees every family on every host; anyone else the server answers sees only their own.

The server adds it up from each session's own usage, every 15 minutes, and the card answers from that sweep ("Reading" until the first one finishes). A window's spend is what a session has spent now minus what it had spent at the window's start (a total that falls, as a restarted status line's does, adds the sample before the fall to a per-session offset, so later spend still counts), taken from a snapshot kept for 35 days in `/data/ae-family-cost.json` (`AE_FAMILY_COST_FILE`; `AE_FAMILY_COST=0` turns the sweep off); days are Pacific time ("today" for the flag amounts too), and a day's snapshot is the last sample before its midnight; a family follows `ae.orch`, parent links, subagents of subagents and handoff chains (an earlier lead is a member of the newest lead's family), and a chat whose parent is gone is a family of its own; a chat that was deleted (not archived) drops out of its family's totals; a chat older than the window counts from the oldest snapshot, and the card says when that history is shorter than the window. Checked on 2026-10-29 against the Claude transcripts: the token totals match to within 1.4%, a Claude lead's total already holds its subagents, and a Codex session's native subagents add tokens but not cost (the parent's cost already includes them). Sessions keep no cache-write figure, so "input" includes cache writes. Family tokens as displayed also count cache reads, so they run higher than the Presets tab's, which leave cache reads out; the token flag leaves them out too (`today.flag_tokens`, input plus output), and a snapshot written before that field existed falls back to the full total until the next sweep. Dollars are estimated at API rates; on a subscription they show where usage goes, not the invoice.

**Where:** The Families tab of the Spend card in the Admin Center; its tile counts the families and turns amber when one passes a flag amount.<br>

## Edit a global policy's parameters

<p align="center"><img src="../media/policies-edit.webp" alt="Edit a global policy's parameters"></p>

Stock Omnigent lets an admin switch a global policy on or off. The fork adds Edit beside the switch: it opens the policy's parameters prefilled, such as the slot cap's limit or the rabbit-hole hours, and the server checks the new values by building the policy before it saves. A slot cap limit set here also sets every slot count in the UI, in place of `AE_SLOT_LIMIT`.

**Where:** Settings > Global Policies: the pencil on a policy with parameters.<br>
**Built from:** core patches [`0094`](../../patches/0094-ae-patch-Check-a-global-policy-s-factory_params-by-b.patch), [`0095`](../../patches/0095-ae-patch-Edit-a-global-policy-s-parameters-on-the-Gl.patch); [`packages/ae_omni_policies`](../../packages/ae_omni_policies)

## Open tabs hear about an update

<p align="center"><img src="../media/reload-notice.jpg" alt="Open tabs hear about an update"></p>

Stock Omnigent keeps running the page a tab loaded, so a fix deployed to the server stays invisible until someone reloads. The fork checks the server's start page every two minutes and whenever the window comes back into view. When the server runs a newer build, a toast says Omnigent was updated, with Reload and Later. Later keeps that tab on the page it has until the next update.

**Where:** Any open tab, after the server is redeployed.<br>
**Built from:** core patches [`0214`](../../patches/0214-ae-patch-Tell-an-open-tab-that-the-server-was-update.patch), [`0215`](../../patches/0215-ae-patch-Spell-Omnigent-the-usual-way-in-the-Reload-.patch)
